# Reading typed input that contains typos: the noise model and the eval3-typo twin (2026-09-28)

Issue #102, the measurement twin of #101. The end-to-end network (#88) should
read typed input that contains typos and still produce the intended sentence --
in `wo zai jai`, the preceding 我在 is what makes `jai` read as 家. Three pieces
were missing: an input representation for typos, a way for the output to reach
the intended characters, and something that measures it. This stage builds the
first and third: one noise model shared by training (#103) and inference (#104),
and `eval3-typo`, a fourth twin of `eval3.jsonl` whose keystrokes carry typos.

## The noise model

The data lives in `crates/ime-pinyin/data/typo.json`, next to the syllable
table, and is generated by `mlime gen-pinyin-tables` from
`python/src/mlime/data/typo_model.json` like the rest of the pinyin data. It is
plain JSON so the Rust side of #104 can read it with serde and nothing else:

- `neighbours`: the symmetric QWERTY adjacency table over a-z, used for
  adjacent-key substitution.
- `fuzzy_pairs`: the directed pairs z/zh, c/ch, s/sh, n/l (initials) and
  an/ang, en/eng, in/ing (finals), each with a `where` of `initial` or `final`
  and a weight. The retroflex direction loses the h more often than it gains
  it (zh to z weighs .55, z to zh .45); the nasal finals split .45/.55 toward
  adding the g; n/l split even.
- `edit_type`: adjacent-key substitution .42, transposition of neighbouring
  letters .14, omission .16, doubling .08, fuzzy-pair swap .20. Fat-finger
  substitution is the dominant typing error; omission and transposition are
  next; doubling is rare. The fuzzy share is what an ordinary keyboard model
  cannot produce -- h is not adjacent to z -- and it is the error class an
  IME user makes by spelling the syllable they hear rather than the one that
  is written.
- `per_sentence` .35: roughly one sentence in three carries a typo at all.
- `edit_count`: 1 edit .62, 2 edits .25, 3 .10, 4 .03, conditional on the
  sentence being corrupted.

The model applies edits to the keystroke string itself: substitution picks a
position and a neighbour key, transposition swaps two neighbouring letters,
omission drops one letter, doubling repeats one, and a fuzzy swap rewrites a
syllable's initial or final at a site the true syllable segmentation provides.
None of the edits can empty the input. `python/src/mlime/typo.py` implements
it; `NoiseModel.maybe_corrupt` (the `per_sentence` coin) is the entry point
#103's training data uses, while the twin generator forces `min_edits=1`,
because the twin measures typo reading and a clean record measures nothing.
Everything is seeded -- `record_seed` hashes (seed, index, clean input, text)
with BLAKE2b-8, so a record's corruption depends on its identity, not its
position in the file.

## The twin

`mlime eval typo-twin --eval-set eval3.jsonl --out eval3-typo.jsonl
--lattice lattice.jsonl` writes one line per eval3 record: `pinyin` is the
corrupted keystroke string, `text` and `context` are untouched, and a new
optional `clean` field keeps the original keystrokes. `EvalRecord`'s dev/test
digest prefers `clean` when present, so eval3-typo slices into the same 498
dev / 5027 test records as eval3 and the other twins -- the comparison is
record-for-record, which is what makes the sanity row below meaningful. The
true syllable boundaries a fuzzy swap needs are taken from the lattice's
character-aligned path (every record has one), and `--lattice` is required:
re-segmenting the keystrokes instead would guess, and a longest-first guess
mis-splits about 7.6% of records and misplaces their fuzzy sites.

5525 records, 8554 edits (1.55 per record -- the twin raises `per_sentence`
to 1):

| edit | count | share |
| --- | --- | --- |
| adjacent | 3650 | 42.7% |
| fuzzy | 1640 | 19.2% |
| omission | 1372 | 16.0% |
| transposition | 1214 | 14.2% |
| doubling | 678 | 7.9% |

940 of the 5525 corrupted strings (17.0%) are no longer segmentable as valid
pinyin under the eval lattice rules (a span must be a full syllable, a
single-letter start of one, or a zh/ch/sh prefix, with no incomplete tail).

A corrupted record that cannot be segmented used to abort `fused-eval`
entirely. `Reader::read` now returns `None` on `NoSegmentation` and the record
is counted `unanswered` -- an honest zero, since no reading of that input
exists. Any other error still raises.

## Why the top-1 is near zero

Three layers fail in sequence:

1. **17% cannot be read at all.** 859 test records (matching the generator's
   940-record segmentability estimate closely; the decoder's segmenter is
   slightly more permissive) have no valid syllable segmentation, so the beam
   never starts. `lkieyyikaankan` has no reading; the record is unanswered,
   not wrong.
2. **The intended characters are usually not candidates.** The lattice
   enumerates readings of the *corrupted* string. `haopachuxianxaita` (好怕
   出现踩踏, `cai` typed `xai`) segments as `... xi an xi ai ta` and the beam
   produces 好怕出现喜爱他 -- a fluent sentence spelled exactly by the
   corruption. 踩踏 is unreachable: no reading in the lattice includes `cai`,
   so its characters never enter a candidate list. Character accuracy (.4256)
   sits well under sentence accuracy's ceiling because roughly every second
   position's correct character is not in the lattice.
3. **The emissions carry no typo prior.** Route A was trained on clean
   keystrokes; on corrupted input it scores readings of the corruption
   confidently. That is why the weight sweep is flat -- raising the emission
   weight trusts a signal that is wrong at exactly the typo positions. What
   rescues a record is the transition side (trigram + char LM) re-reading the
   context when the corruption still leaves the intended reading reachable:
   `kongpasguyideba` (恐怕是故意的吧, `shi` typed `s`) and
   `bixushizoudaon` (必须是走到哪, `na` typed `n`) both decode correctly,
   while `shougepoqianwandeerchuantshiping` comes back 首个破千万的二传提示屏
   against 首个破千万的二创视屏.

And top-8 (1.31%) barely exceeds top-1 (1.19%): the right sentence is absent
from the beam, not merely outranked. This is the honest baseline -- a fusion
system that reads only the spelled string cannot see past the typo. Fixing it
is what #103 (a reader trained on this distribution) and #104 (a decoder that
can reach characters the string does not spell) are for; the noise model and
the twin are the shared contract both sides build against.

## Reproduce

```sh
# regenerate the shared data file and the twin (deterministic)
python/.venv/bin/mlime gen-pinyin-tables
python/.venv/bin/mlime eval typo-twin \
  --eval-set data/run3_pool/eval3.jsonl \
  --out data/run3_pool/eval3-typo.jsonl \
  --lattice data/route-a-assets-v2/lattice.jsonl

# sanity row (reproduces the published eval3 number within int8 quantization)
ime-cli fused-eval --model data/run3/ngram.bin \
  --lm data/char-lm-run/transformer-s1/char-lm-int8 --lm-weight 1 \
  --eval-set data/run3_pool/eval3.jsonl \
  --emittable data/route-a-assets-v2/emittable.txt \
  --route-a data/route-a-export/int8 --slice test --weight 1

# eval3-typo: dev sweep, then test at the dev-selected weight
ime-cli fused-eval --model data/run3/ngram.bin \
  --lm data/char-lm-run/transformer-s1/char-lm-int8 --lm-weight 1 \
  --eval-set data/run3_pool/eval3-typo.jsonl \
  --emittable data/route-a-assets-v2/emittable.txt \
  --route-a data/route-a-export/int8 --select-on-dev \
  --weight 0 --weight 0.25 --weight 0.5 --weight 0.75 \
  --weight 1 --weight 1.25 --weight 1.5 --progress <dir>
```

The runs above took about 15 minutes (sanity) and 30 minutes (sweep + test)
on an 8-core x86 box with route-a at its default of one intra-op thread per
rayon worker. Give the towers more than one thread per worker and ORT's
spin-wait threads oversubscribe the cores several-fold.

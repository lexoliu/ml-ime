# ml-ime for agents

A neural Chinese pinyin input method that reads the text already on screen. The deliverable is
beating the commercial input methods (Sogou, Baidu, Apple, RIME) on all three ways people type:
full pinyin, first-letter abbreviations, and the mix of both. Every stage ends in a note under
`notes/` with the model, the tables, how to reproduce them, and what comes next; the notes are the
project's record, and a stage without its note is not finished.

## How the pieces fit

```
corpora (crates/ime-corpus, ime-synth) ──> sample shards ──> labels (mlime train labels)
        │
        ▼
route A on Kaggle: context encoder + non-autoregressive fill decoder (mlime train route-a)
        │  emits per-position scores over each evaluation lattice (mlime train emit)
        ▼
ime-cli fused-eval: beam search over the emissions with a transition —
        the trigram (ime-ngram) or the character LM (ime-lm), alone or fused
        │
        ▼
notes/<stage>.md
```

The character LM is trained with `mlime train char-lm` (resumable across sessions) and
exported with `mlime export char-lm`: `charlm.onnx` (one step over a batch of beams),
`prefill.onnx` (the context once per record), the external weights files, and `charlm.json`, the
manifest that names every tensor. `ime-lm` loads that directory; a graph without its manifest
table does not load, so an export and the decoder always move together.

## Layout

| Path | What it holds |
| --- | --- |
| `crates/ime-pinyin` | syllable inventory, character lexicon, segmentation lattice, homophone masks; `data/` is generated by `mlime gen-pinyin-tables` and CI fails when it is stale |
| `crates/ime-decode` | the `Emission` and `Transition` traits and the beam search |
| `crates/ime-ngram` | the trigram: baseline and transition |
| `crates/ime-lm` | the character LM as a stateful transition over ONNX Runtime, weights shared across threads |
| `crates/ime-neural` | inference for the context encoder and the fill decoder |
| `crates/ime-eval` | evaluation sets, slices and metrics |
| `crates/ime-cli` | the command line: `fused-eval`, `train-ngram`, and the rest |
| `crates/ime-corpus`, `ime-g2p`, `ime-synth` | corpus fetching, dual pinyin annotation, grounded synthesis of slang usage |
| `python/` | the `mlime` CLI (uv project): corpus, labels, training, export, `eval generate` / `eval rime` |
| `kaggle/`, `colab/` | the training kernels and the Colab launcher; `kaggle/README.md` |
| `notes/` | the record |
| `macos/ContextProbe` | the accessibility probe for reading the host application's text |
| `data/` | everything generated or downloaded: eval sets, score files, models, exports, run outputs; never committed |

## Measurement

- Three evaluation twins under `data/run3_pool`: `eval3.jsonl` (full pinyin),
  `eval3-abbreviated.jsonl`, `eval3-mixed.jsonl`, each with its own score file
  (`scores-lattice*-context-on.jsonl.gz`).
- The dev slice is a hash of the record (`--dev-share 0.0905`), so it survives reordering.
  Weights are chosen on dev (`--select-on-dev`) and reported on test; never tune on test.
- Metrics: sentence top-1 and top-8 (or top-k at a wider beam, the oracle), character accuracy,
  MRR. The current numbers to beat are in `notes/search-diversity.md`, `notes/char-lm-v2.md` and
  `notes/commercial-baselines.md`.
- A change to the protocol (slices, weights, beam width, what counts as correct) is its own
  issue; it is never folded into a model comparison.

## Working here

- English in code, comments, commits and notes; Chinese appears only as data.
- Issue first, then a branch, then a pull request to `dev` whose body says `Fixes #N`.
- Rust: a workspace with strict lints; check per crate (`cargo check -p`, `cargo clippy -p
  --all-targets -- -D warnings`, the crate's tests). Python: `uv run --project python …`,
  `ruff`, `mypy`, `pytest`.
- Secrets live in `.env` (`MLIME_LLM_*` for the LLM endpoint) and are never printed or committed.

## Compute

- Before any step that would burn more than 30 minutes of compute, stop and make it faster
  first: Rust instead of Python, parallelism across records, SIMD, a GPU, a batched shape. The
  slow version does not get run "just this once" so that the optimisation can come next time;
  most runs have no next time.
- Estimate the cost first — model calls × cost per call ÷ the throughput the target machine
  reaches at that batch size — and write the estimate in the issue.
- Anything that will run for more than an hour must be resumable: it checkpoints its progress
  and, started again, continues from where it stopped instead of from the beginning. That is
  what makes it possible to stop at any moment, make the algorithm faster, and carry on. Training
  resumes from `run/charlm.pt`; an evaluation grid resumes per finished section and, within a
  section, from the last record whose result was written.
- A long run must saturate what it runs on. Running for hours at under 80% utilisation of the
  resource that bounds it (the cores, the GPU, memory bandwidth) is forbidden: it means the
  work is shaped wrong — too few rows a step, too few records in flight, a serial stage — and
  the shape is fixed before the run continues. Check utilisation once the run has warmed up and
  again at every wake, and record it with the run.
- A GPU test on a training VM runs after the kernel's `install()`, in the environment the leg
  trains in.
- A GPU assignment refused for capacity (503) is retried after a pause, never in a loop; nothing
  is billed until a runtime is assigned.
- A performance measurement on a training card is training: every configuration starts from
  the run's checkpoint and keeps its own, and the winner continues from its checkpoint. A leg
  that is thrown away buys the same steps and discards them.
- A grid never repeats a configuration already shown to be redundant. Once a cheaper
  configuration has matched the expensive one on the dev slice, the grid runs the cheaper one and
  the expensive one is a single check.
- The decoder's shape is the product's: one sentence, eight beams a step. Its per-step cost is
  the input method's latency, so the levers there are bytes per weight and a faster backend, not
  more threads.

## GPUs

- No Devin, local or cloud, works on this repository: its code runs straight on expensive GPUs,
  so it is written by a coordinating session or an Opus subagent and reviewed before any GPU
  runs it.
- Training runs only on an A100 or a G4, never an H100. A T4 or L4 checks GPU training code for
  correctness and trains nothing: its legs publish nothing and their weights are discarded. Code
  that is not GPU training code is covered by unit tests, not GPU checks.
- No A100 or G4 training starts without the owner's explicit permission, asked with the
  correctness and performance checks complete and the expected training time.
- Every Colab runtime carries the watchdog; nothing outlives its controller. Cost is stated in
  compute units, together with time.
- `data/` is not regenerable and is never deleted without asking.
- The e2e step is bound by kernel launches, so the host's cores decide the card, and memory is
  never the limit (about 10 GB of VRAM). The G4 (RTX PRO 6000 Blackwell, 96 GB, 48-core host)
  costs about 9 CU/h and is the training card: 0.355 s/step on the v2 epoch at 91.5%
  utilisation, 0.542 s/step on the ranking stage at 85%. The A100 40 GB (12-core host, 5.3 CU/h)
  starves on launches: 0.719 s/step at 75%. The L4 is power-capped at 72 W, so a launch
  optimisation shows nothing on it. #155 holds the comparison.
- Colab sessions are run from the Mac mini, the only machine whose `colab` resolves their
  names. The owner watches one with
  `ssh -t lexoliu@lexos-mac-mini 'TERM=xterm-256color /Users/lexoliu/.local/bin/colab ssh -s <session>'`.
  `colab exec` exits 0 when the remote code raises; `colab/provision.sh`'s `remote` reports the
  real outcome.
